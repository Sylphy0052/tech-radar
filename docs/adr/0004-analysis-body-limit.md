# ADR 0004: 解析へ渡す本文長の上限

- ステータス: 採用
- 日付: 2026-08-12
- 関連: `PROJECT_SPEC.md` §9, §24 / Issue #73, #74 / [ADR 0001](0001-technology-stack.md), [ADR 0002](0002-llm-tool-isolation.md)

## コンテキスト

記事解析は本文を `body[:MAX_ANALYSIS_BODY_CHARACTERS]` へ切ってから LLM へ渡す（`backend/src/techradar/analysis/service.py`）。この値は実装時に 12000 と置いたまま、根拠がコードにも `docs/` にも残っていなかった。

Issue #17 の「未確定・後続で判断する事項」に挙がっていた3項目のうちの1つであり、実データが溜まった段階で実測して確定することにしていた（Issue #73）。計測そのものの土台は Issue #74 で `techradar.measure` として用意した。

## 計測

本番 DB（記事 194 件、2026-08-12 時点）を読み取り専用で参照して測った。再現手順は末尾に置く。

### 1. 本文長の分布

| 指標 | 値 |
| --- | --- |
| 記事数 | 194 |
| 最小 | 355 |
| p25 | 2242 |
| 中央値 | 3684 |
| p75 | 9191 |
| p90 | 15936 |
| p95 | 20969 |
| p99 | 52463 |
| 最大 | 546409 |

上限別の切り捨て率は次のとおり。

| 上限 | 超過件数 | 割合 |
| --- | --- | --- |
| 4000 | 91 | 46.9% |
| 8000 | 59 | 30.4% |
| 12000 | 30 | 15.5% |
| 16000 | 19 | 9.8% |
| 24000 | 8 | 4.1% |

最大の 546409 文字は OpenSSH のリリースノート全体を1ページに連結したもので、通常の技術記事とは性質が違う。次点は 63048 文字であり、この1件だけが大きく外れている。

### 2. 本文長に対する応答時間

同じ記事の本文を複数の長さへ切り、解析と同じ指示・同じスキーマで Claude Code CLI を呼んで所要時間を測った（代表記事 2 件 × 5 通りの長さ × 3 回 = 30 回、うち成功 28 回）。

| 本文長 | 中央値 | 最小 | 最大 | 失敗 |
| --- | --- | --- | --- | --- |
| 2000 | 8.9 秒 | 7.8 | 11.8 | 0 |
| 4000 | 8.7 秒 | 8.0 | 10.1 | 0 |
| 8000 | 10.0 秒 | 8.9 | 10.2 | 1 |
| 12000 | 10.2 秒 | 9.3 | 11.8 | 1 |
| 16000 | 10.4 秒 | 9.1 | 11.0 | 0 |

本文長を 8 倍にしても中央値は 8.9 秒から 10.4 秒へ 17% しか伸びない。同じ長さでの実行ごとのばらつき（7.8〜11.8 秒）の方が大きく、**この範囲では応答時間は本文長にほぼ依存しない**。

### 3. 切り捨てが解析結果へ与える影響

上限を超える記事について、「12000 文字で切った本文」と「全文」の解析結果を比較した（記事 8 件、うち比較できたのは 7 件）。

あわせて対照実験も行った。**同じ全文を2回解析して同じ指標で比較する**（`--control`）。LLM は同じ入力でも実行ごとに出力が揺れるため、これを測らないと、観測された差が切り捨て由来なのか実行ごとのばらつき由来なのか区別できない。対象記事は通常モードと同じ 8 件を使った。

| 指標 | 切り捨て版 vs 全文版 | 全文版 vs 全文版（対照） |
| --- | --- | --- |
| domain 一致率 | 85.7% | 100.0% |
| category 一致率 | 57.1% | 57.1% |
| content_type 一致率 | 100.0% | 100.0% |
| difficulty 一致率 | 71.4% | 85.7% |
| topics の Jaccard 中央値 | 0.25 | 0.11 |
| technologies の Jaccard 中央値 | 0.78 | 0.78 |
| technical_quality の差の中央値 | 0.00 | 0.00 |

**切り捨てによる差は、同じ入力を2回解析したときのばらつきと同程度である。** topics に至っては対照のほうが中央値が低い（0.11 < 0.25）。category と technologies と technical_quality は両モードで同じ値になった。domain と difficulty は切り捨て側がやや低いが、7 件中 1 件の違いであり、ばらつきの範囲を超えているとは言えない。

補強材料として、比較した記事のうち最も短いもの（12107 文字）は上限を 107 文字（0.9%）超えるだけである。入力はほぼ同一にもかかわらず topics の Jaccard は 0.43 だった。

## 決定

**`MAX_ANALYSIS_BODY_CHARACTERS` は 12000 のまま維持する。**

引き上げも引き下げもしない。

### 根拠

- **処理時間は決め手にならない。** 本文長を 8 倍にしても応答時間は 17% しか伸びず、実行ごとのばらつきに埋もれる。上限を上げても遅くならないが、下げても速くならない
- **上げる利得が検出できない。** 切り捨てによる解析結果の差は、同じ入力を2回解析したときの差と同程度だった。上限を 12000 から 16000 へ上げると切り捨て対象は 15.5% から 9.8% へ減るが、それによって解析結果が良くなることを示す材料が無い
- **下げる理由も無い。** 下げれば切り捨て率が上がる（8000 なら 30.4%）一方、応答時間は縮まない

つまり実測した範囲では、この値を動かす理由が見つからなかった。「根拠が無いまま 12000 だった」状態から「実測したうえで 12000 を選んでいる」状態へ変えることが、この ADR の内容である。

### この測定で言えないこと

- **比較したのは 12107〜15430 文字の 7 件のみ**である。上限の 1.3 倍までしか見ていない。52463 文字や 546409 文字のような、上限の 4 倍・45 倍を切り捨てる場合に差が出ないとは言っていない
- **差が「無い」ことを証明したわけではない。** LLM 出力のばらつきが大きく、7 件では小さな差を検出できない。言えるのは「切り捨ての影響がばらつきに埋もれる程度である」ことまで
- **出力の良し悪しは判定していない。** 差の有無だけを見ており、どちらの要約が優れているかは測っていない
- 記事 194 件は RSS の新着に偏っている。母集団全体の分布を代表するとは限らない

上限の 4 倍を超える切り捨てが問題になるとすれば、それは巨大ページ（リリースノート全体、目次ページ）の本文抽出そのものの問題でもある。上限の調整ではなく抽出側で扱うべき事象であり、この ADR の範囲外とする。

## 副産物として分かったこと

決定そのものには影響しないが、計測の過程で観測した事実を記録する。

- **LLM の出力は同じ入力でも安定しない。** 対照実験で、同一の全文を2回解析したときの category 一致率は 57.1%、topics の Jaccard 中央値は 0.11 だった。推薦は `topics` を使うため（`recommendation/ranking.py`）、この揺れが推薦結果へどう波及するかは別途見る必要がある
- **構造化出力がスキーマを外すことがある。** 計測中に `LLMInvalidResponseError: 応答がスキーマを満たしません` が発生した（応答時間の計測で 30 回中 2 回、切り捨て比較で 8 件中 1 件）。長さとの相関は見られず、同条件で 6 回追試したところ全て成功した。実運用は `complete_json_with_retry` が 3 回までリトライするため吸収される

## 再現方法

いずれも本番 DB を読み取り専用で参照する。DB へは書かない。

```bash
cd backend

# 1. 本文長の分布と切り捨て率（クラスタ・フィード枠の集計も含む）
uv run python -m techradar.measure

# 2. 本文長に対する応答時間
uv run python -m techradar.measure.run_llm_latency --lengths 2000,4000,8000,12000,16000 --repeats 3 --articles 2

# 3. 切り捨てが解析結果へ与える影響
uv run python -m techradar.measure.run_truncation_impact --articles 8

# 4. 3 の対照実験（同じ全文を2回解析したときのばらつき）
uv run python -m techradar.measure.run_truncation_impact --articles 8 --control
```

2〜4 は Claude Code CLI を実際に呼ぶ。3 と 4 は同じ記事集合を対象にするため、`--articles` と `--limit` を揃えて実行する。
