# ADR 0007: 新規性を embedding 距離で測る

- ステータス: 採用
- 日付: 2026-08-14
- 関連: `PROJECT_SPEC.md` §8, §14, §15 / Issue #75, #87, #88, #89 / [ADR 0003](0003-embedding-runtime.md) / [ADR 0006](0006-cluster-count-and-feed-slot-defaults.md)

## コンテキスト

`compute_novelty`（`backend/src/techradar/recommendation/ranking.py`）は当初、候補記事の `topics` のうちユーザーの既知トピック集合（`InterestProfile.known_topics`）に無いものの割合を返していた。既知かどうかは正規化した文字列の一致で判定していた。

Issue #75 で既定値を実測しようとした際、この式が実データで機能していないことが分かった。フィードの多様性確保枠（diversity、定員 5）に入る候補が 0 件で、枠が常に他枠からのあふれだけで埋まっていた。

原因は、LLM が付ける `topics` が記事ごとの固有名詞に近く、語がほとんど再利用されない点にある。2026-08-13 の実測（関心記事 69 件 / 候補 169 件）では次のとおりだった。

- `known_topics` 337 語に対し、候補側の topics 語彙は 832 語（延べ 843）。重なりはわずか 13 語
- その結果 novelty は 1.0 が 153 件、0.8 が 15 件、0.6 が 1 件。連続値にならず上端へ張り付く
- 実際の topics の例: 「AGENTS.md への規則の外出し」「AI ファシリテーションのリファインメント」「8列グリッド設計」。いずれも一度しか現れない

閾値では直せないことも確認した。上位 2 枠に取られない候補 39 件について `exploration_min_novelty` を上げても、39 件全てが novelty 1.0 のため、取りうる最大値 1.0 まで上げて分岐しなかった。

## 決定

`compute_novelty` を embedding のコサイン類似度ベースへ差し替える。

```text
novelty = clamp01(1 - max(cosine_similarity(candidate.embedding, e.vector) for e in profile.embeddings))
```

「最も近い関心記事 1 件からどれだけ遠いか」を測る。候補に embedding が無い、または関心プロファイルが空なら比較できないため `novelty.default_when_no_embedding`（0.5）を返す。

topics による判定は残さず撤去する。フォールバックとして併存させると、候補ごとに値の意味が変わり採点経路が 2 本になるため。この結果、`InterestProfile.known_topics` は読み手が無くなるので併せて削除した。

### 最大値を使う理由

`compute_interest_similarity` は上位 `top_k` 件の加重平均を取る。novelty をその裏返し（`1 - interest_similarity`）にすると、`composition.py` の `_slot_for` は 1 段目（strong_interest）と 3 段目（exploration）で同じ値の表裏しか見られなくなる。最大値を使えば別の統計量になり、strong_interest を外れた候補が exploration と diversity へ分岐しうる。

## 計測

本番 DB（記事 261 件・関心記事 69 件・候補 169 件、2026-08-14 時点）を読み取り専用で参照して測った。再現手順は末尾に置く。

### 1. novelty の分布

| 指標 | 変更前（topics 未知率） | 変更後（embedding 距離） |
| --- | --- | --- |
| 最小 | 0.6 | 0.135 |
| p25 | 1.0 | 0.430 |
| 中央値 | 1.0 | 0.523 |
| p75 | 1.0 | 0.610 |
| p95 | 1.0 | 0.671 |
| 最大 | 1.0 | 0.754 |
| 1.0 に張り付いた件数 | 153 / 169 | 0 / 169 |

変更前の列は Issue #87 に記録された 2026-08-13 の実測（1.0 が 153 件、0.8 が 15 件、0.6 が 1 件）から導いた。旧実装には novelty の分布を出す計測が無かったため、同じ計測モジュールで測り直したものではない。変更後の列は `techradar.measure` の出力そのものである。

上端への張り付きが解消し、連続的な分布になった。上限が 0.754 に留まるのは、候補が「ユーザーが購読している情報源から集めた技術記事」であり、関心プロファイルと完全に無関係な記事が母集団に存在しないためで、想定どおりである。

### 2. 枠ごとの充足率

`page_size` は本番の `limits.feed_run_size`（100）。

| 枠 | 定員 | 変更前 選択 / 補充 | 変更後 選択 / 補充 |
| --- | --- | --- | --- |
| strong_interest | 55 | 55 / 0 | 55 / 0 |
| primary_source | 25 | 25 / 0 | 25 / 0 |
| exploration | 15 | 15 / 0 | 15 / 0 |
| diversity | 5 | 5 / **5** | 5 / **0** |

変更前は diversity 枠の 5 件すべてが他枠からのあふれ（補充）だった。変更後は自前の候補で埋まる。ドメイン重複を避ける `_select_primary` の制約が、これで初めて効く。

### 3. 閾値の選定

`exploration_min_novelty` を 0.1 刻みで動かし、上位 2 枠に取られなかった候補 39 件がどう分岐するかを数えた。

| 閾値 | exploration | diversity |
| --- | --- | --- |
| 0.0〜0.4 | 39 | 0 |
| 0.5 | 34 | 5 |
| **0.6（採用）** | **16** | **23** |
| 0.7 | 1 | 38 |
| 0.8〜1.0 | 0 | 39 |

定員は exploration 15 / diversity 5。両枠が自前の候補で埋まるのは 0.6 だけである。0.5 では diversity がちょうど定員と同数で余裕が無く、0.7 では exploration が 1 件しか残らず補充頼みになる。現行値 0.6 を据え置く。

この表は `_slot_for` による 1 件ずつの分類を数えたもので、`compose_feed_with_stats` が行う定員の適用・他枠からの補充・ドメイン重複の排除（`_select_primary`）は通っていない。示しているのは「その閾値なら各枠にいくつの候補が入りうるか」であって、最終的なフィードの中身ではない。0.6 で実際に枠が埋まることは、上記 2.（枠ごとの充足率）が `compose_feed_with_stats` の結果として裏付けている。

## 却下した案

- **topics を正規化して部分一致を許す。** 小文字化・記号除去に加えて複合語を分割する案。LLM の出力形式へ依存し続ける点が変わらず、固有名詞中心の topics では改善幅が読めない
- **プロンプトを変えて topics を語彙の限られた分類語にする。** 既存記事 261 件の再解析が必要になる。得られるものに対して実行コストが見合わない
- **`1 - interest_similarity`（top_k 加重平均の裏返し）を使う。** 上記「最大値を使う理由」のとおり、枠判定が同じ軸の表裏になる

## 影響

- 設定キー `novelty.default_when_no_topics` を `novelty.default_when_no_embedding` へ改名した（値 0.5 は据え置き）。`backend/config/scoring.yaml` を手で書き換えている環境では追随が要る
- embedding が未生成の記事は novelty が 0.5 に固定される。変更前は topics さえあれば値が出ていた。実データの候補 169 件では該当が無く、影響は観測されなかった
- `InterestProfile.known_topics` を削除した。関心プロファイルからトピック語彙を読む経路は無くなる
- `interest_similarity` と同じ embedding 空間を見るため、両者の相関は残る。実測では最大値を使うことで枠が分岐したが、関心プロファイルの偏り方によっては再び縮退しうる。その場合は閾値ではなく式を再検討する

## 追記: 相関の実測（2026-08-14、Issue #88）

上記「影響」の最後に書いた相関を、Issue #88 で計測できるようにして測った。同じ実データ（記事 261 件・関心記事 69 件・候補 169 件）での値は次のとおり。

| 指標 | 値 |
| --- | --- |
| novelty と interest_similarity の Spearman 順位相関 | **-0.991** |
| strong_interest / primary_source を外れた候補 39 件のうち diversity 行き | 23 件（59.0%） |

2 つの指標は母集団が違う。相関は候補 169 件すべてを対象にし、偏り率は上位 2 枠を外れた 39 件だけを対象にする。前者は軸そのものの重なりを、後者は現行の閾値 0.6 の近傍で実際に何が起きているかを見ている。片方からもう片方は導けない。

**相関は -0.991 で、ほぼ完全な相補である。** 「最大値を使えば `interest_similarity`（top_k 加重平均）とは別の統計量になる」という上記の設計判断は、この実データではほとんど効いていない。両者は実質的に同じ軸の裏表として振る舞っている。

それでも枠が分岐しているのは、閾値 0.6 が分布の中に位置しているからにすぎない。偏り率 59.0% は 0% にも 100% にも寄っておらず、現時点で枠は機能している。しかし軸が 1 本しか無い以上、関心プロファイルの分布が動けば `strong_interest_min_similarity`（0.5）と `exploration_min_novelty`（0.6）の 2 つの閾値が同じ軸の上で近づき、片方の枠が空になる状態へ戻りうる。**Issue #87 で直したのは飽和であって、軸の冗長性そのものは残っている。**

この状態を「正常時の基準値」として記録する。次に測ったとき相関が -1.0 へさらに近づくか、偏り率が 0% / 100% へ張り付いていたら、閾値ではなく式を見直す段階である。式を別軸にする案（クラスタ重心からの距離、情報源やトピックの分布に基づく多様性など）は、そのときに検討する。

## 追記: 式の差し替え（2026-08-14、Issue #89）

上の Issue #88 の追記に「次に測ったとき相関が -1.0 へさらに近づくか、偏り率が 0% / 100% へ張り付いていたら、閾値ではなく式を見直す段階である」と書いた。実際には、-0.991 という値そのものが既に「軸が 1 本しか無い」ことを示していた。偏り率が中間にあるのは閾値がたまたま分布の中にあるからにすぎず、閾値を動かす余地があることと、軸が独立していることは別である。Issue #89 で式を差し替えた。

### 比較した式

同じ実データ（記事 261 件・関心記事 69 件・候補 163 件・クラスタ 8 個、2026-08-14 時点）で 6 つの式を測った。相関は novelty と interest_similarity の Spearman 順位相関で、受入基準は |相関| < 0.9。

| 式 | 相関 | 最小 | p25 | p50 | p75 | 最大 |
| --- | --- | --- | --- | --- | --- | --- |
| 現行（関心記事の最大類似度） | -0.991 | 0.135 | 0.427 | 0.515 | 0.607 | 0.754 |
| A: クラスタ重心の最大類似度 | -0.979 | 0.184 | 0.405 | 0.515 | 0.600 | 0.738 |
| A': クラスタ重心の加重平均 | -0.967 | 0.273 | 0.462 | 0.564 | 0.645 | 0.777 |
| B: 候補集合との平均距離 | -0.910 | 0.579 | 0.681 | 0.714 | 0.749 | 0.871 |
| B': 候補集合の最近傍距離 | -0.612 | 0.094 | 0.333 | 0.449 | 0.508 | 0.762 |
| C: 情報源の目新しさ | -0.563 | 0.594 | 0.783 | 1.000 | 1.000 | 1.000 |

**当初の第一候補だった A（クラスタ重心からの距離）は基準を満たさなかった。** クラスタ重心は関心記事群の平均であり、関心記事そのものと同じ embedding 空間の同じ領域を指すため、「最も近い関心記事 1 件」を「最も近いクラスタ重心 1 個」へ置き換えても軸は変わらない。A' も同様である。実装前に測ったことでこれが分かった。

C（関心記事に現れた情報源ドメインとの照合）は相関が最も低いが、値の半数以上が 1.0 に張り付く。Issue #87 で直した飽和そのものであり、採用できない。

B（候補集合の全候補との平均距離）は基準を満たすが、分布が 0.579〜0.871 の狭い帯に集まる。平均を取ることで候補集合全体の重心からの距離に近づき、個々の候補の違いが潰れるためである。

### 採用した式

A と B' の min を採用した。

```text
cluster_part  = clamp01(1 - max(cos(candidate.embedding, centroid) for centroid in cluster_centroids))
neighbor_part = clamp01(1 - max(cos(candidate.embedding, other) for other in 同じ採点対象の他の候補))
novelty       = min(cluster_part, neighbor_part)
```

B' 単独（-0.612）でも基準は満たすが、A を合成する。B' だけだと「既知の関心のど真ん中にある記事でも、今回の候補集合にたまたま似た記事が無ければ新規」と判定されてしまう。逆に A だけでは上表のとおり軸が独立しない。2 成分の min を取ることで「既知のクラスタから離れており、かつ今回の候補集合の中でも孤立している」候補だけが高い値を得る。

合成方法は 3 つ測った。

| 合成 | 相関 | 最小 | p25 | p50 | p75 | 最大 |
| --- | --- | --- | --- | --- | --- | --- |
| **min(A, B')（採用）** | **-0.687** | 0.094 | 0.320 | 0.429 | 0.501 | 0.738 |
| 相乗平均 sqrt(A × B') | -0.831 | 0.211 | 0.375 | 0.459 | 0.545 | 0.750 |
| 算術平均 (A + B') / 2 | -0.876 | 0.213 | 0.382 | 0.472 | 0.547 | 0.750 |

3 つとも基準は満たすが、平均系は A の寄与が残るぶん相関が高い。min は「両方の条件を満たすこと」を要求する合成で、意味の上でも上記の意図と一致する。

`cluster_centroids` は `user_interest_clusters` テーブルから読まず、`build_interest_profile`（`recommendation/service.py`）の中で `interest/clusters.py` の構築処理を呼んでその場で計算する。テーブルの中身は `rebuild_interest_clusters` ジョブを回さないと更新されず、未構築・古いまま推薦を回すと novelty が既定値へ張り付いて Issue #87 と同じ縮退を別の形で踏むためである。

`neighbor_part` は候補どうしの総当たり（O(n^2)）になるため numpy の行列積で一括計算し、`rank_candidates` から `score_candidate` へ渡す。次元 1024 での実測は次のとおりで、numpy を明示的な依存へ追加した（従来は scikit-learn 経由の推移的依存でしか入っていなかった）。

| 候補数 | 純 Python の総当たり | ノルム事前計算 + 上三角 | numpy 行列積 |
| --- | --- | --- | --- |
| 163（実データ） | 2.08 秒 | 0.43 秒 | 0.14 秒 |
| 500（`max_candidates_per_run` の上限） | 20.41 秒 | 4.38 秒 | 0.14 秒 |
| 1000 | 計測せず | 18.25 秒 | 0.22 秒 |

値は同じ機械での 1 回の実測で、負荷によって振れる（`CLAUDE.md` の「混んでいる機械では check.sh が落ちる」参照）。桁が問題であり、numpy 以外は候補数の上限 500 で採点 1 回あたり数秒から数十秒を足すことになる。

### 閾値の再選定

式が変われば分布も変わるため、`exploration_min_novelty` を測り直した。上位 2 枠に取られなかった候補 37 件の分岐は次のとおり。

| 閾値 | exploration | diversity |
| --- | --- | --- |
| 0.3 | 32 | 5 |
| 0.4 | 31 | 6 |
| **0.5（採用）** | **19** | **18** |
| 0.6 | 2 | 35 |
| 0.7 | 1 | 36 |

定員は exploration 15 / diversity 5。両枠が自前の候補で埋まるのは 0.4 と 0.5 だけで、0.5 の方が diversity 側の余裕（定員 5 に対し 18 件）が大きい。**0.6 から 0.5 へ引き下げた。** 旧式での 0.6 は据え置きの結論だったが、新式では diversity 側へ寄りすぎて exploration が 2 件しか残らず補充頼みになる。

この表が `_slot_for` による 1 件ずつの分類であって最終的なフィードの中身ではない点は、上の「3. 閾値の選定」と同じである。0.5 で実際に枠が埋まることは、直前の充足率の表が `compose_feed_with_stats` の結果として裏付けている。

### 残る制約

- **`neighbor_part` は候補集合に依存する。** 同じ記事でも、一緒に採点される候補が変われば novelty が変わる。「その記事が絶対的にどれだけ新規か」ではなく「今回のフィードの中でどれだけ浮いているか」を測る値である。フィードの構成を決めるための指標なので用途とは合っているが、記事単位で保存された過去の novelty と時点をまたいで比較することはできない
- **相関 -0.687 は独立ではない。** 基準は満たすが、`cluster_part` が `interest_similarity` と同じ embedding 空間を見る以上、負の相関は残る。ここからさらに下げるには、embedding 以外のシグナル（情報源の分布、トピックの時系列など）を入れる必要がある。上表の C がその方向だが、単独では飽和する
- **記事起点推薦（`_build_article_based_profile`）では、起点記事 1 件を唯一の中心として `cluster_centroids` に入れる。** このプロファイルに関心クラスタは無いが、空のままにすると `compute_novelty` が既定値 0.5 を返して候補ごとの差が全く付かなくなる（`reasons.novelty` も一律になる）。起点記事からの距離を新規性とみなすのは、Discover が関心クラスタ群の重心からの距離を使うのと同じ意味である。なお記事起点推薦は `composition.py` を通らないため、この値は枠判定ではなく順位付けと理由表示にだけ効く

## 再現手順

```bash
cd backend
uv run python -m techradar.measure          # 人が読む表形式
uv run python -m techradar.measure --json   # 機械可読な JSON
```

novelty の分布・閾値表は出力の `novelty` 以下、枠ごとの充足率は `feed` 以下にある。集計の実装は `backend/src/techradar/measure/novelty.py` と `backend/src/techradar/measure/feed_slots.py`。枠の判定は自前で持たず `recommendation.composition` の `_slot_for` をそのまま呼ぶため、測っている対象は本番の挙動と一致する。
